Jarvis — Architecture Deep-Dive

A personal multi-agent operating system. One orchestrator daemon, ~90 specialist agents, a two-layer memory, and a 4-tier safety model — built on the Claude Agent SDK. Every function name below is real code from jarvis_core/.

01 How a message enters the system

Boss types on Telegram → the bridge forwards it over HTTP to a long-running local daemon. If the daemon is down, it falls back to spawning the Claude CLI directly.

Interface
Telegram bot · @jarvis_Ujjawal_Bot
Runs as a systemd service (jarvis-bridge). Also: voice, cron briefings.
↓
Bridge
bridge/telegram_bridge.py
Async httpx POST to the daemon. Short connect-timeout so a dead daemon fails over fast.
_call_via_daemon() → POST http://127.0.0.1:8765/chat
↓
Brain
jarvis-core daemon (FastAPI + Uvicorn)
Bound to 127.0.0.1 only — no public port. Holds all state in memory, survives across requests.
@app.post("/chat") → the 4-stage pipeline below
Why a daemon and not just the CLI? A long-running service keeps conversation state, memory, and the goal-scheduler warm in memory — no cold start per message, and background work (autonomous goals) can run between chats.

02 The /chat pipeline — 4 stages

This is the heart. Inside daemon.py:chat(), every message flows through four layers. Stages 1 & 2 run in parallel (independent), then the worker, then a silent critic.

STAGE 1 + 2 (parallel)
Intent classify and memory recall are independent — fired together via asyncio.create_task + asyncio.to_thread.
Stage 1 · Intent
jarvis_core/intent.py
A cheap Haiku call sorts the message into 8 categories + priority + confidence. 3s timeout. Slash-commands become a synthetic task.
IntentClassifier.classify()
→ <intent category="task" .../>
Stage 2 · Recall
jarvis_core/recall.py
Semantic search over past memory in ChromaDB. Keeps only hits scoring ≥ 0.55, trims to a 2000-token budget. Skips greetings / short msgs.
Recaller.gather()
→ <jarvis_memory_context>…</>
↓  augmented_prompt = intent + memory + user message
Stage 3 · Worker
jarvis_core/orchestrator.py → run_worker()
Spawns a Claude Code session via the Agent SDK, in the Jarvis project dir — so the worker sees all ~90 agents, MCP tools, skills, CLAUDE.md. Streams output, captures session_id (for resume) + cost.
run_worker(prompt, resume_session_id, max_turns…)
↓
Stage 4 · Critic
jarvis_core/critic.py → Critic.evaluate()
A silent Haiku reviewer scores the draft on 4 rubrics — Intent · Memory · Claims · Tone. Verdict revise → exactly one revision pass. Attaches a confidence tag. Never blocks the reply (fails open).
_review() → JSON verdict  ·  _revise() → clean rewrite
↓
Response
ChatResponse → back to Telegram
Carries reply, confidence, memory_hits, revised, intent, priority. The turn is logged for auto-capture.
The one-liner to memorize: "Intent + Recall run in parallel, then the Worker answers with full memory context, then a silent Critic verifies it against four rubrics and can revise once — all inside one FastAPI endpoint."

04 The orchestrator — one worker vs. a fleet

Everything that talks to Claude goes through run_worker(). Auth is a Max-subscription OAuth token (CLAUDE_CODE_OAUTH_TOKEN) — no developer API key.

Single worker — /chat

  • One Claude session, resumable via session_id.
  • Runs with cwd = Jarvis root, so it inherits all agents + tools.
  • Streaming collected into one text; cost + session captured.

Parallel fan-out — /task

  • run_parallel_workers() spawns N workers with asyncio.gather.
  • Each worker = its own independent context window.
  • Wall-clock = the slowest worker, not the sum.
  • aggregate_results() synthesizes all outputs into one.
This is the "Manager–Worker" pattern. The daemon is the manager; each run_worker call is a specialist doing focused work. Parallel-by-default is a stated design principle.

05 The memory layer — two layers

The part that makes Jarvis feel like it "knows me." Structured facts + a searchable history.

Layer 1 · Structured files

  • data/memory/ — facts, preferences, projects, people, habits.
  • Human-readable Markdown with type: / zone: frontmatter.
  • Loaded at session start; edited by the memory-agent.

Layer 2 · Vector DB (episodic)

  • ChromaDB + sentence-transformers embeddings.
  • Every past conversation chunked & embedded.
  • EpisodicMemory.recall() = semantic search.
  • Auto-capture cron ingests new facts every 30 min.
Recall flow (before every reply)
user msg → Recaller.gather() → ChromaDB top-k → filter score ≥ 0.55 → trim to 2000 tokens → <jarvis_memory_context> injected into the worker prompt
In one word: this is RAG over my own history — retrieval-augmented generation, where the knowledge base is everything Jarvis has ever learned about me.

06 Autonomous goals — the overnight brain

Boss hands Jarvis a goal (/goal_add); it plans, executes safe parts itself, and parks risky parts for morning approval. A background GoalScheduler polls every 60s.

QUEUED→ PLANNING→ RUNNING→ AWAITING_APPROVAL→ COMPLETED  | FAILED / CANCELLED
1 · Plan
decomposer.py → decompose_goal()
One Haiku call returns strict JSON (validated by Pydantic DecompositionPlan): 1–8 sub-tasks, each tagged Tier 1/2/3. Single-level only — no recursive sub-goals. Malformed/unsafe → REFUSED:.
↓
2 · Execute
scheduler.py → _run_goal_inner()
Tier 1 & 2 sub-tasks run concurrently (asyncio.gather). Tier 3 sub-tasks create an ApprovalRequest and the goal parks at AWAITING_APPROVAL. Tier-3 never auto-runs overnight.
↓
3 · Guardrails
Budget + duration caps
Cost > max_budget_usd ($5 default) → FAILED. Elapsed > max_duration_seconds (2h default) → FAILED. On restart, orphaned RUNNING goals re-queue cleanly.
↓
4 · Approve & finish
resume_goal_after_approval()
Boss replies /goal_approve → the Tier-3 sub-task executes now; once all Tier-3s resolved, _synthesize_final() stitches outputs and the goal → COMPLETED. Morning digest summarizes it all.

07 The 4-tier safety model

Every action Jarvis can take is classified. The decomposer assigns the tier; the scheduler enforces it. This is the human-in-the-loop guarantee.

TIER 1Auto, silent. Reads, research, drafts, screenshots, summaries — no side effects. Just runs.
TIER 2Auto + audit log. Local writes: files in the Jarvis repo, memory, calendar events, Notion pages, browser form fill (not submit). Logged to data/audits/.
TIER 3Confirm required — always. Irreversible external actions: send email, submit a form, publish, delete, git push, payment. Gated on Boss's explicit approval even in full-auto mode.
TIER 4Permanently refused. Destructive system ops, phishing, auth bypass, ToS violations. No mode override — the planner returns REFUSED:.
