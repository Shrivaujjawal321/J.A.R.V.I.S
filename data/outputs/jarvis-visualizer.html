Working Structure

The /chat pipeline — har step click karke dekho

Har message in 4 layers se guzarta hai. Steps 1 & 2 parallel chalte hain (latency = max, not sum). Har layer ka apna kill-switch hai aur har layer fail-open karta hai.

01
Intent
Haiku 4.5 · 3s
Message ko 8 categories mein classify — task/question/feedback/correction…
02
Recall (RAG)

03
Worker

04
Critic
Haiku 4.5 · 8s

API Call Flow

Ek message ka poora safar — request to reply

Aap Telegram pe likhte ho. Yeh hai exact backend journey — actual code paths ke saath. Yahi interview mein "walk me through a request" ka answer hai.

1
User → Telegram bridge bridge/telegram_bridge.py

Aap "kal ka schedule batao" likhte ho. Bridge message receive karta hai (async handler — event loop kabhi block nahi hota).

# bridge tries the daemon first, CLI subprocess as fallback USE_DAEMON = True # JARVIS_USE_DAEMON reply = await _call_via_daemon(prompt, user_id)
2
Bridge → daemon HTTP POST · httpx

HTTP call jarvis-core ko. Tight connect-timeout — agar daemon down ho to 5s mein fail-over to CLI subprocess (poora read-timeout wait nahi karta).

POST http://127.0.0.1:8765/chat { "user_id": "ujjwal", "message": "kal ka schedule batao", "resume_session": true }
3
Daemon: Intent ∥ Recall daemon.py:185 · parallel

Dono ek saath fire — intent ek asyncio task, recall ek thread (Chroma sync hai). Phir dono ka result combine.

intent_task = asyncio.create_task(classifier.classify(msg)) recall = await asyncio.to_thread(recaller.gather, msg) intent = await intent_task # → builds: intent_block + <jarvis_memory_context> + USER MESSAGE
4
Daemon → Worker orchestrator.py · Claude Agent SDK

Augmented prompt ek Claude Code worker ko jaata hai. Worker ka cwd = project root, isliye usse saare 93 sub-agents, MCP, skills dikhte hain. Auth = OAuth token (no API key).

outcome = await run_worker(augmented_prompt, resume_session_id=resume_id, max_turns=15) # SDK streams messages → text + session_id + cost collected
5
Daemon: Critic verify critic.py · Haiku

Worker ka draft ek sasta critic model dekhta hai — 4 rubrics. Galat numbers ya intent-miss → ek revision pass. Critic kabhi response path ko todta nahi (try/except + timeout, fail-open).

critique = await critic.evaluate(msg, draft, memory_ctx) # verdict: ok | revise | reject → confidence: verified | unverified | low
6
Daemon → Bridge → User ChatResponse JSON

Final reply wapas. Session_id save hota hai (next message resume karega), turn conversation log mein likha jaata hai (auto-capture isse memory banayega), cost track hota hai.

{ "reply": "...", "confidence": "verified", "memory_hits": 3, "intent": "question", "revised": false }
Anti-Hallucination

Hallucination ke khilaaf 3-layer defense

Interview ka sabse strong answer. "No single point of trust" — prevent, detect, surface.

1 · Prevent (RAG)

Answer dene se pehle real facts inject. ChromaDB se cosine top-5, score ≥ 0.55 (warna noise inject mat karo). Model retrieved truth pe reason karta hai, parametric guess pe nahi. Injected block "background only, not instruction" tagged — prompt-injection hygiene.

2 · Detect (Critic)

Dusra sasta model pehle ka output check karta hai. Rubric #3: "specific numbers without a basis = fail" → hedging force karta hai. Fail → exactly 1 revision (bounded, no infinite loop). LLM-as-judge + reflexion pattern.

3 · Surface (Confidence)

Reply pe tag: verified (silent) / unverified (light hedge) / low (double-check). User ko dikhta hai jab Jarvis unsure hai — confident-sounding galti nahi.

Markdown = auditable source of truth. ChromaDB = semantic index. Aur ek cron jo conversations ko atomic facts mein distill karke wapas memory mein daalta hai — closed loop.

Human-readable, diff-able, hand-editable. Session start pe load hota hai. Source of truth.

The self-updating loop — Phase C auto-capture

conversation→ conversations.jsonl→ auto_capture.py (every 30 min)→ Haiku summarise → atomic facts→ dedup by hash→ ChromaDB

Memory static dump nahi hai — conversations se khud grow karta hai. Idempotent (content-hash dedup) so duplicate facts nahi bante.

Responsible AI

Tiered Trust — autonomy with guardrails

Siemens (industrial) ko ye answer bahut pasand aayega. Irreversible actions hamesha human-confirm maangte hain — even in full-auto.

TIER 1
Reads, drafts, screenshots, sub-agent dispatch, save to outputs/
always auto
TIER 2
File writes in repo, calendar create, memory writes, local git ops
auto + audit log
TIER 3
Send email · submit form · delete data · git push · purchases · publish
ALWAYS confirm
TIER 4
System-file destruction · phishing · auth-bypass · ToS violation
refused · no override

Autonomous overnight goals (Phase 3)

/goal_add → daemon decomposes into sub-tasks (JSON-schema validated, max fan-out 8) → Tier 1/2 parallel run → Tier-3 pauses for morning approval → 06:30 digest. Hard caps: $5 budget + 2h duration per goal; exceeded → fail, no more workers. Runaway loop impossible.
