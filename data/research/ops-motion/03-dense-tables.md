# Research Brief: Dense Operational Data Tables at Scale (2026)

**Question:** How do best-in-class 2026 products build data-dense tables that stay fast, readable and usable — including on a phone — and what is the concrete implementation playbook?

**Scope note:** This is a US freight carrier dispatch console — fleet register, driver roster, loads board, trips board, audit log, a 43-row RBAC matrix, detention billing. 8-10 columns, status chips, progress bars, inline row actions, multi-select. ~8 demo rows today, thousands in production. Must work at 900px and 375px.

---

## Quick Answer

For an operator tool at this scale (low thousands of rows, not millions), pair **TanStack Table (headless logic) + TanStack Virtual (row virtualization)** on top of native `<table>` markup, keep filters/sort/pagination-vs-scroll state in the URL (e.g. via `nuqs`), use a **fixed comfortable-default density with a compact toggle**, and at 375px **do not try to shrink the desktop grid** — collapse each row into a card with the identity fields pinned and a details drawer for the rest. Selection needs an explicit page-vs-all-matching-filter distinction to avoid the classic "select all" trap. Accessibility for a virtualized grid is not free — you have to add `aria-rowcount`/`aria-rowindex` and, per AG Grid's own accessibility docs, the safest documented fix when full a11y compliance is required is to disable virtualization or fall back to pagination for the DOM ([AG Grid Accessibility](https://www.ag-grid.com/react-data-grid/accessibility/)) — worth deciding deliberately rather than discovering it late.

## Evidence Per Topic

### 1. Virtualization

- **TanStack Virtual vs react-window vs react-virtuoso:** TanStack Virtual (16.8M weekly downloads) and react-window (6.3M, more stars but stale/no active development) are both mature; react-virtuoso is described as "the pragmatic choice" for teams that want dynamic heights, grouping, sticky headers and infinite scroll **out of the box** rather than building them headless. TanStack Virtual is the right pick when you want maximum flexibility and are willing to compose sticky/variable-height behavior yourself. ([npm trends](https://npmtrends.com/@tanstack/virtual-core-vs-react-virtualized-vs-react-virtuoso-vs-react-window), [react-virtualization showdown](https://mashuktamim.medium.com/react-virtualization-showdown-tanstack-virtualizer-vs-react-window-for-sticky-table-grids-69b738b36a83))
- **TanStack Table's own docs treat Table + Virtual as the standard pairing** for enterprise-scale row counts ([TanStack Table Virtualization Guide](https://tanstack.com/table/latest/docs/guide/virtualization)).
- **Sticky headers/columns + virtualization is a known, unresolved rough edge**, not a solved problem you can copy-paste. A live TanStack GitHub discussion lays out the exact trade-off you will hit: absolute-positioned row layout (needed for row virtualization) breaks sticky columns; table-layout-based approaches keep sticky columns working but the sticky header/footer visually "escapes" and scrolls past content near the bottom because it's bound by the oversized virtual container ([TanStack/virtual Discussion #872](https://github.com/TanStack/virtual/discussions/872)). A separate open issue confirms sticky headers can disappear entirely when virtualization is combined with certain scroll-container setups ([TanStack/virtual Issue #640](https://github.com/TanStack/virtual/issues/640)). **Budget explicit engineering time for this** — it is the single riskiest integration point in the whole table stack. TanStack does ship a working column-pinning-sticky example to start from ([Column Pinning Sticky Example](https://tanstack.com/table/latest/docs/framework/react/examples/column-pinning-sticky)).
- **AG Grid** (for comparison/fallback): renders only visible rows plus a configurable buffer — default 10 rows above/below (≈420px at the 42px default row height), with a hard safety cap of 500 rendered rows regardless of buffer settings. Column virtualization has no buffer because horizontal scroll is treated as less CPU-intensive. Variable/auto row heights shrink the effective buffer (a 100px row height only fits ~5 buffer rows in the same pixel budget), which is a real perf consideration if your progress-bar/chip cells cause row-height variance. ([AG Grid DOM Virtualisation docs](https://www.ag-grid.com/react-data-grid/dom-virtualisation/))
- **Expandable rows + virtualization**: not directly documented for TanStack in the sources found — treat detail-expansion rows as **dynamic-height virtual items** (TanStack Virtual supports variable sizing via `measureElement`) rather than a separate DOM structure. `[inferred]`
- **Accessibility breaks when you virtualize**, plainly: screen readers only perceive the rows/cells actually in the DOM, so a virtualized table silently reports a wrong (much smaller) row count and users can't find rows that aren't rendered. The documented fix is `aria-rowcount` (total rows), `aria-rowindex` (each item's real position), and `aria-colcount` on the container, with `aria-rowcount="-1"` when the true total isn't known yet ([a11ysupport.io aria-rowcount](https://a11ysupport.io/tech/aria/aria-rowcount_attribute), summarized from [GitHub microsoft/fluentui #26197](https://github.com/microsoft/fluentui/issues/26197)). **AG Grid's own accessibility documentation goes further and recommends disabling row/column virtualization outright, or using pagination instead, when full screen-reader compliance is required** — because grouped columns and dynamic focus changes still trip up several screen readers even with correct ARIA row/col attributes ([AG Grid Accessibility](https://www.ag-grid.com/react-data-grid/accessibility/)). This is a real design decision for your audit-log and RBAC-matrix tables, which are the ones most likely to be reviewed by compliance/accessibility-conscious users — consider non-virtualized + paginated for those two specifically. `[inferred: which of your 7 tables need this — audit log and RBAC matrix are the most compliance-sensitive by nature]`

### 2. 60fps at scale

- **Root causes of jank in big tables**, synthesized from multiple sources: layout thrash from unstabilized row heights, per-row/per-cell event handler allocation on every render, re-render storms when parent state changes cascade into every visible row, and expensive cell renderers (custom formatting, inline SVG, computed styles) run per-cell instead of memoized.
- **CSS containment / `content-visibility: auto`**: skips layout, paint and (optionally) size work for off-screen content. Measured results found in research: one benchmark showed CSS containment dropping render time from ~11s to ~500ms for a large table; a separate content-visibility benchmark on 10,000 rows reported sub-second render vs. ~500ms baseline improvements, and a real-world emoji-picker case study reported ~45% combined load-time improvement (from ~3s to ~1.3s) after adding `content-visibility: auto` ([LogRocket: CSS content-visibility](https://blog.logrocket.com/using-css-content-visibility-boost-rendering-performance/), [Nolan Lawson: Improving rendering performance with content-visibility](https://nolanlawson.com/2024/09/18/improving-rendering-performance-with-css-content-visibility/), [Cory Rylan: High Performance HTML Tables with Lit and CSS Contain](https://coryrylan.com/blog/high-performance-html-tables-with-lit-and-css-contain), [MDN content-visibility](https://developer.mozilla.org/en-US/docs/Web/CSS/content-visibility)). Note: `content-visibility` and JS virtualization solve overlapping but distinct problems — virtualization skips *rendering the DOM at all*, `content-visibility` skips *layout/paint work* for DOM nodes that still exist. They compose (containment on the virtualized row wrapper is still worth doing) but `content-visibility` is not a substitute for virtualization at genuinely large row counts.
- **Memoization strategy**: `React.memo` on row/cell components + `useCallback` for handlers passed down, so a parent re-render doesn't cascade. Libraries built on TanStack Table (Material React Table, Mantine React Table) expose an explicit `memoMode` (cell / row / table-body) precisely because table re-render cost is a known problem class — but they also warn that aggressive memoization can silently break features like drag-reorder or resize if you're not careful about what state escapes the memo boundary ([Material React Table Memoization Guide](https://www.material-react-table.com/docs/guides/memoization), [Mantine React Table Memoize Components Guide](https://www.mantine-react-table.com/docs/guides/memoize-components)).
- **Event delegation**: prefer one click handler on the table body (delegated via `event.target` inspection / data attributes) over one closure per row for row-actions — avoids per-row function allocation on every render. `[inferred — standard React perf practice, not found as a named citation in this research pass]`
- **Avoid per-cell components** where a plain function returning JSX will do — component instances carry React reconciliation overhead (fiber nodes, hooks) that a plain render function does not.

### 3. Column strategy on narrow screens

This is covered in depth in the dedicated section below ("What to do with a 10-column table at 375px"). Summary of what real products do:
- **Salesforce Lightning**: fluid 12-column grid system with named breakpoints at 320/480/768/1024px; the `lightning-datatable` component supports resizable columns via keyboard (Tab to the divider, arrow keys to resize) but Lightning's guidance is oriented around *layout* responsiveness more than *column-hiding* strategy specifically ([Salesforce Lightning Datatable docs](https://developer.salesforce.com/docs/platform/lightning-component-reference/guide/lightning-datatable.html), [Create Responsive Layouts](https://developer.salesforce.com/docs/atlas.en-us.mobile_offline.meta/mobile_offline/ux_layout.htm)).
- **Linear**: does not linearize its (issue list) tables at all in the traditional sense — instead uses a custom `ResponsiveSlot`/`ResponsiveSlotContainer` component pair that measures available width via `ResizeObserver` and hides *lower-priority UI elements* (not columns per se) rather than relying on fixed breakpoints ([awesome-design-md Linear DESIGN.md](https://github.com/voltagent/awesome-design-md/blob/main/design-md/linear.app/DESIGN.md)). This priority-based, measured-not-guessed approach is the more sophisticated 2026-tier version of "priority+ pattern."
- **Named patterns across the industry**: three recurring named patterns are (a) **horizontal overflow / pinned-column** — keep the identity column fixed, scroll the rest, most reliable for **operator tools** where users compare fields across a row rather than scan a single value; (b) **priority/transitional collapse** — hide lower-priority columns below a breakpoint, reveal on demand; (c) **card/list transformation** — turn each row into a stacked key-value card, best for consumer/read-heavy contexts ([ninjatables Mobile-First Table Design](https://ninjatables.com/mobile-first-table-design-principles/), [CSS-Tricks: Accessible, Simple, Responsive Tables](https://css-tricks.com/accessible-simple-responsive-tables/)).
- CSS-Tricks' breakdown (still the most-cited reference on this despite its age) names four approaches with accessibility notes: **Squash** (no layout change, only viable for short content), **Horizontal scroll** (trivial `overflow: auto`, preserves table semantics, but users can miss the scrollbar so needs a visible affordance), **Collapse by rows** (`display: table` → `display: block`, keeps markup, gets tall fast), **Collapse by columns** (requires abandoning pure-CSS table markup and reflowing with JS, since `<tr>` locks row-major DOM order) ([CSS-Tricks](https://css-tricks.com/accessible-simple-responsive-tables/)). The same source found via manual screen-reader testing that neither ChromeVox nor VoiceOver correctly announced headers on some of these transformed layouts without extra heading markup — a caution that any column-collapse solution needs explicit a11y testing, not just visual QA.

### 4. Selection and bulk actions

- **The select-all-across-pages trap is real and well-documented.** The fix used by mature design systems is to explicitly separate **scope levels**: row-level, page-level ("select page" — everything on the current visible page/viewport) and global/all-matching-filter ("select all N results") — and to always show the resolved count, e.g. "24 selected on this page — Select all 1,842 matching" ([PatternFly Bulk Selection](https://www.patternfly.org/patterns/bulk-selection/), [HashiCorp Helios Table multi-select](https://helios.hashicorp.design/patterns/table-multi-select)). PatternFly explicitly states the selected-count label must reflect the *total* across pages if "select all" spans pages, not just the visible page — never let the count silently under-report scope.
- **Bulk action bar pattern**: the cleanest implementation is a contextual toolbar that *replaces* the default table toolbar the instant ≥1 row is selected, placed in the same slot the eye already expects controls (i.e., directly above the table) ([eleken: Bulk action UX](https://www.eleken.co/blog-posts/bulk-actions-ux)). PatternFly specifies the bulk selector itself should be the first item in that toolbar for consistent scanning ([PatternFly Bulk Selection](https://www.patternfly.org/patterns/bulk-selection/)).
- **Shift-click range selection**: standard pattern — track a "last selected" anchor index, on shift-click select the contiguous range between anchor and clicked row.
- **Destructive bulk actions**: group destructive actions away from routine ones visually, require a confirming modal that states the exact count and consequence ("Deactivate 14 drivers?"), and prefer undo-after-the-fact over block-before when the action is reversible; block-before (typed confirmation, e.g. type "DELETE") only for truly irreversible/high-blast-radius operations ([eleken](https://www.eleken.co/blog-posts/bulk-actions-ux), [UX Movement: Better Bulk Actions](https://uxmovement.substack.com/p/a-better-ux-approach-to-bulk-actions)). For your detention-billing and RBAC-permission tables specifically, bulk edits are high-consequence (money, access control) — bias toward typed/explicit confirmation over quiet undo. `[inferred, applying general guidance to your specific tables]`
- Selection state should persist across pagination/filtering until the user explicitly clears it, not silently reset ([PatternFly](https://www.patternfly.org/patterns/bulk-selection/)).

### 5. Inline editing vs drawer vs modal

Consensus across sources ([Pencil & Paper: UX Pattern Analysis for Enterprise Data Tables](https://www.pencilandpaper.io/articles/ux-pattern-analysis-enterprise-data-tables), [PatternFly Inline Edit](https://www.patternfly.org/components/inline-edit/design-guidelines/), [UX Design World: Best Practices for Inline Editing](https://uxdworld.com/inline-editing-in-tables-design/), [SaaSUI: Modal/Dialog UX Patterns](https://www.saasui.design/blog/saas-modal-dialog-ux-patterns)):

- **Inline edit-in-place**: right when the edit is a single field, low-risk, and the user benefits from seeing neighboring rows/columns for context while editing (e.g., correcting a single detention-billing rate, toggling a status chip). Requires visible affordance (hover pencil / click-to-edit), and explicit save/cancel controls — not silent auto-commit on blur for anything consequential.
- **Drawer (side panel)**: right when editing a *record*, not a cell — multiple related fields, and the user benefits from keeping the table/list visible for context (e.g., editing a full driver's compliance profile from the roster). Pencil & Paper notes most mature admin panels default to a drawer for exactly this reason — it's the middle ground between the "cramped" inline edit and the "loses all context" modal.
- **Modal**: right for short, focused, must-complete-or-cancel tasks — confirmations, quick-create, or destructive-action warnings. Wrong for anything requiring reference back to the table underneath.
- **Bulk edit** specifically should switch orientation — turn the horizontal table row into a vertical form (in a modal or drawer), since editing multiple fields across multiple selected rows doesn't fit a horizontal table layout at all ([UX Movement: bulk edit](https://uxmovement.substack.com/p/the-easiest-way-to-bulk-edit-data)).
- Applied to your console: status chips and single numeric fields (rate, quantity) → inline. Driver/vehicle compliance records, RBAC row edits → drawer. Deleting/deactivating, multi-row edits → modal. `[inferred mapping onto your specific tables]`

### 6. Sorting, filtering, faceting

- **Multi-column sort**: default to single-column sort as the common case; shift-click a header to add secondary/tertiary sort keys, with a small numbered badge (1, 2, 3) next to each active sort arrow showing priority order ([DataTables multi-column ordering](https://datatables.net/examples/basic_init/multi_col_sort.html), [TanStack Table Sorting Guide](https://tanstack.com/table/v8/docs/guide/sorting)). One dissenting note worth flagging: shift-click is rare in web UI generally and effectively undiscoverable without a hint — Adrian Roselli's multi-column sortable table experiment is worth reading before committing to this as the *only* affordance ([Adrian Roselli: Multi-Column Sortable Table Experiment](http://adrianroselli.com/2021/06/multi-column-sortable-table-experiment.html)). `[inferred: consider a small "+ add sort" affordance as an alternative/supplement to bare shift-click for discoverability]`
- **Sort state accessibility**: use `aria-sort="ascending"|"descending"` **only on the currently-sorted column header**, never on more than one at a time, and never the literal value `"none"` (omit the attribute instead) — a specific, easy-to-get-wrong detail per Adrian Roselli, who also flags that JAWS announces `aria-sort` changes automatically but NVDA and TalkBack do not, so a live region announcing "Sorted by [column], ascending" is still needed for full coverage ([Sortable Table Columns — Adrian Roselli](http://adrianroselli.com/2021/04/sortable-table-columns.html)).
- **Filter chips vs filter panel**: the panel is the control surface for *adding* filters; chips below the search/toolbar area are the *display* of currently-applied filters, individually removable, syncing back into the panel state ([Innovaccer Table Filters](https://design.innovaccer.com/patterns/tableFilters/usage/)). A filtered table that visually looks identical to an unfiltered one is flagged as a real failure mode — active filters must stay visibly present, not hide in a collapsed panel ([Setproduct 2026 Data Table Guide](https://www.setproduct.com/blog/data-table-ui-design)).
- **Saved views**: personal by default (each user's own saved filter set); to share a view with the team, share the URL, since saved-view state should be URL-encoded anyway ([SaaSUI: Filtering & Sorting UX](https://www.saasui.design/blog/saas-filtering-sorting-ux-patterns)).
- **URL as state store**: use `nuqs` (or equivalent typed URL-param library) to keep filters, sort, pagination cursor, and even selection scope in the URL — this is exactly the pattern the `openstatusHQ/data-table-filters` reference implementation follows for a production-grade filterable data table ([nuqs.dev](https://nuqs.dev/), [openstatusHQ reference](https://deepwiki.com/openstatusHQ/data-table-filters/6.1-url-state-management)). This directly satisfies your "dispatcher can share a link to exactly what they're looking at" requirement.

### 7. Pagination vs infinite scroll vs virtualized-all

- **Pagination wins for operational/task tools.** The consistent framing across sources: pagination suits contexts where users need structure, want to jump back to a specific known position, or need a stable, referenceable/bookmarkable set (exactly your dispatch console use case — "load #4821 was on page 3 of the loads board"). Infinite scroll suits *discovery* browsing where absolute position doesn't matter ([LogRocket: Pagination vs Infinite Scroll](https://blog.logrocket.com/ux-design/pagination-vs-infinite-scroll-ux/), [Setproduct 2026 guide](https://www.setproduct.com/blog/data-table-ui-design)).
- **What breaks with infinite scroll in a work tool**: loses back-button/scroll-position reliability, makes "share a link to this exact row" impossible without extra engineering, makes total-count context ("47 open loads") ambiguous, and interacts badly with in-place row updates (a live status change can reflow rows out from under a scrolling user).
- **Virtualization threshold**: the practical guidance found is "necessary past roughly 1,000 rows" for client-rendered tables, but the deciding factor should be *task*, not raw row count — pagination remains correct even at high row counts if users are doing deliberate lookup rather than scanning ([Setproduct 2026 guide](https://www.setproduct.com/blog/data-table-ui-design)).
- **Recommended for your console**: server-side paginate + filter/sort, then virtualize the rendered page/window client-side. This gives stable URLs, bounded DOM, and avoids the infinite-scroll failure modes above, while still handling "thousands of rows" without ever rendering them all.

### 8. Accessibility

- **Table semantics**: real `<table>`, `<thead>`, `<th scope="col">` (and `scope="row"` for row headers where relevant) — semantic HTML gives most of this "for free," which is exactly why Adrian Roselli argues `role="grid"` is usually the wrong choice for a data table: "My general rule is that you should probably ignore ARIA grid unless you are trying to recreate Excel" ([ARIA Grid as an Anti-Pattern](http://adrianroselli.com/2020/07/aria-grid-as-an-anti-pattern.html)). His critique specifically calls out libraries like ag-Grid for defaulting div-heavy grid-role markup onto what is really just a data table, and flags that ARIA grid's arrow-key navigation model actively conflicts with normal tab-based expectations, varies across screen reader implementations, and breaks under reflow/zoom for responsive layouts.
- **However**, your RBAC permission matrix (43 rows × presumably many permission columns, likely with inline toggle controls per cell) is closer to the "Excel-like, genuinely interactive grid" case Roselli carves out as the legitimate use for `role="grid"` — that's the one table in your console where the WAI-ARIA grid pattern is probably the right call, not the exception. `[inferred, applying his stated exception to your specific RBAC table]`
- **WAI-ARIA Authoring Practices grid pattern** (when you do need it): keyboard model is roving-tabindex-based — arrow keys move the single active cell, Home/End jump to row start/end, Ctrl+Home/Ctrl+End jump to the whole grid's start/end; Tab does not move between cells, the whole grid is one tab stop ([WAI-ARIA Data Grid Examples](https://www.w3.org/TR/2019/NOTE-wai-aria-practices-1.1-20190814/examples/grid/dataGrids.html)).
- **Roving tabindex implementation**: only one cell has `tabIndex={0}` at a time, all others `-1`; on arrow-key press, move focus and flip which cell owns the `0`. Off-the-shelf React hooks exist (`react-roving-tabindex`, Mantine's `use-roving-index`) but their own docs caution they're built for small-to-medium grids — "if you need a roving tabindex in a very large grid or table (a few hundred cells or more) then you will likely be better served with a bespoke implementation" ([react-roving-tabindex GitHub](https://github.com/stevejay/react-roving-tabindex), [Mantine use-roving-index](https://mantine.dev/hooks/use-roving-index/)). Your fleet register at thousands of rows × 8-10 columns will exceed that "few hundred cells" comfort zone fast if fully virtualized+interactive — expect to write custom focus management, not drop in the library as-is. `[inferred synthesis]`
- **Sortable columns**: `<button>` inside `<th>`, SVG sort-direction indicator marked `aria-hidden="true"` (so it isn't double-announced), `aria-sort` only on the active column, live-region announcement of sort changes since not all screen readers announce `aria-sort` state changes automatically ([Adrian Roselli: Sortable Table Columns](http://adrianroselli.com/2021/04/sortable-table-columns.html)).
- **WCAG 2.2 AA specifics** that apply: 24×24px minimum target size for interactive controls (relevant to your compact-density row actions and checkboxes — don't let "compact" density shrink checkboxes/buttons below this), programmatically-determinable sort/filter state, keyboard-operable everything, visible focus indicators meeting the 2.2 contrast requirements ([Setproduct citing WCAG 2.2](https://www.setproduct.com/blog/data-table-ui-design), [botmonster: Accessible Data Table Sorting/Filtering/Keyboard Nav](https://botmonster.com/web-dev/accessible-data-table-sorting-filtering-keyboard-navigation/)).
- **Virtualization + accessibility tension is the load-bearing open question here** — see §1's `aria-rowcount`/`aria-rowindex` fix and AG Grid's own "just disable virtualization for full compliance" fallback recommendation. Decide per-table which side of that tradeoff you're on (see Open Questions).

### 9. Density

- **Named modes, not one fixed value**, is the consistent recommendation. Adobe Spectrum ships exactly three: compact, regular ("comfortable"), spacious, controlled via a `density` prop on `TableView` ([React Spectrum TableView](https://react-spectrum.adobe.com/TableView), [Spectrum Design Data — Table](https://opensource.adobe.com/spectrum-design-data/components/table)).
- **Concrete px values found in research** (these vary by source — treat as a reasonable range, not a spec): "Standard density typically uses 48–56px for comfortable reading and touch-friendly interaction, while compact density ranges from 40–44px for maximum data visibility" (general synthesis, source: search-engine-aggregated design guidance, not a single primary citation — flagged accordingly). A separate, more specific source (Carrie Lee's enterprise data table guidelines) gives named values: **Condensed 40px / Regular 48px / Relaxed 56px** ([Data Tables for Enterprise Applications](https://medium.com/@calee607/data-table-design-guidelines-for-enterprise-applications-40f7ef0e0186)). Setproduct's more recent 2026 guide deliberately declines to prescribe an exact number, instead anchoring compact rows to WCAG 2.2's 24×24px minimum interactive target and Material Design 3's 48dp touch minimum as the *floor*, and recommending designers set the exact value against their own type scale rather than borrow a number ([Setproduct 2026 guide](https://www.setproduct.com/blog/data-table-ui-design)). **Recommendation**: use 40-44px compact / 48-52px comfortable as your two modes, never let compact rows drop checkbox/action-button hit targets below 24px even if the row itself is 40px (pad the interactive element, not just the row).
- **Make it a user preference, persisted.** Power users (dispatchers doing all-day triage) strongly prefer compact; occasional/oversight users (auditors, drivers checking one load) prefer comfortable — this split is called out consistently enough across sources to treat as settled, not open. Persist per-user, not per-session.

## What to do with a 10-column table at 375px

This is the concrete decision you asked for. Based on the pattern evidence above (§3, and CSS-Tricks' four-pattern breakdown), here is the recommendation with the reasoning and the rejected alternatives:

**Recommendation: card/list transformation, not horizontal scroll, for the primary mobile view — with a details drawer for anything beyond 3-4 surfaced fields.**

**Why, specifically for a 10-column operator table at 375px:**

1. **Horizontal scroll fails the "one-handed in a truck cab" test.** Even with a pinned identity column, scrolling 6-7 remaining columns on a 375px viewport means each additional column gets a sliver of width — status chips and progress bars (which your tables have) become illegible or get truncated, and users very often don't realize more columns exist off-screen (a specifically-named failure mode in the mobile-first table research: "users may not know that the table is scrollable and may not see all of the fields"). For a dispatcher glancing at a phone, silently missing a column (e.g., a HOS violation flag) is a real operational risk, not just an aesthetic one.
2. **Priority-column collapse (hide columns, reveal on demand) is a reasonable middle ground but wrong as your primary strategy** because at 10 columns you'd likely need to hide 6-7 of them to fit 375px, which means the "collapsed" default view is barely more informative than a card would be, while still carrying the cognitive baggage of "this is a table with hidden stuff" rather than the more mobile-native card mental model.
3. **Card/list transformation is what the pattern research consistently recommends for this exact width class**, and it maps naturally onto what a dispatcher actually needs at 375px: the *identifying* field (load #, driver name, truck unit #) plus 2-3 *status* fields (chip, progress) at a glance, tap to open a **drawer** (or full-screen sheet at this width) with the remaining 6-7 fields and any inline actions. This matches the general "collapse by rows → stacked key-value card" pattern and the "priority table" concept where the primary column is always shown and the rest is revealed on tap ([ninjatables Mobile-First Table Design](https://ninjatables.com/mobile-first-table-design-principles/), [Setproduct 2026 guide](https://www.setproduct.com/blog/data-table-ui-design)).
4. **Pick the 2-3 surfaced fields per table deliberately, not generically** — this needs a per-table decision, not a single global rule:
   - Loads board: load ID, status chip, pickup/delivery window or ETA.
   - Trips board: trip ID, driver, status.
   - Fleet register: unit #, status/compliance chip, next-maintenance-due indicator.
   - Driver roster: driver name, HOS-remaining or compliance chip, current assignment.
   - Detention billing: load ID, amount, status (paid/pending/disputed).
   - Audit log: timestamp + actor + action summary (naturally list-like already — this one may not need a card transform at all, a simple stacked log-line view works).
   - RBAC matrix (43 rows × permission columns): this one is structurally different — a permission matrix doesn't compress into a 3-field card meaningfully. Recommend a **role-picker + single-role detail view** at narrow widths (pick a role, see its full permission list as a vertical list) rather than trying to render the matrix at all on a phone. `[inferred — no direct source addresses matrix/grid tables specifically at mobile width; this is a reasoned extrapolation from the "card doesn't work for truly 2D data" principle]`
5. **900px is a different decision** — at 900px (tablet/small-laptop width), the priority-column collapse or pinned-column horizontal scroll becomes viable again, since you likely have room for 5-6 of the 8-10 columns without illegible cramming. Use `ResizeObserver`-driven, measured column-priority hiding (Linear's approach) rather than fixed Tailwind-style breakpoints, since your columns' natural widths vary by table (a status chip is narrow, a driver name is variable-width) ([awesome-design-md Linear DESIGN.md](https://github.com/voltagent/awesome-design-md/blob/main/design-md/linear.app/DESIGN.md)).
6. **Rejected: "just shrink the desktop grid."** Every source that discusses this calls it out by name as the definitive anti-pattern — see the Anti-Patterns section below.

## Anti-Patterns and the Failure Each Causes

| Anti-pattern | Failure it causes |
|---|---|
| Shrinking the desktop grid to fit mobile width | Text becomes unreadable, tap targets drop below the 24×24px WCAG 2.2 minimum, status chips/progress bars become meaningless slivers |
| Horizontal scroll with no visible scroll affordance | Users don't discover the hidden columns exist; silently miss data — dangerous for compliance/HOS-flag columns specifically |
| `role="grid"` on a table that's really just tabular data, not an Excel-like interactive surface | Confusing keyboard model (arrow-key nav instead of Tab), inconsistent screen reader behavior, breaks under zoom/reflow ([Adrian Roselli](http://adrianroselli.com/2020/07/aria-grid-as-an-anti-pattern.html)) |
| Virtualizing without `aria-rowcount`/`aria-rowindex` | Screen reader users perceive a table with far fewer rows than actually exist and have no way to reach off-screen rows |
| `aria-sort` applied to multiple columns at once, or set to `"none"` literally | Violates the ARIA spec's intended usage and produces inconsistent screen reader output ([Adrian Roselli](http://adrianroselli.com/2021/04/sortable-table-columns.html)) |
| Silent bulk "select all" that actually only selects the current page | Users think they've selected/will act on all matching rows and only affect the visible page — classic operational error (or the reverse: think they only affected the page and actually hit every matching row) |
| Infinite scroll on an operational/lookup table | Loses back-navigation reliability, unshareable state, ambiguous total counts, rows shifting under active users during live updates |
| Per-row inline components with fresh closures every render | Re-render storms, GC pressure, dropped frames during scroll on thousands of rows |
| Fixed single density for all users | Power users (dispatchers) fight cramped/sparse rows all day; occasional users struggle with too-dense compact mode |
| A filtered view that looks visually identical to the unfiltered view | Users misread partial data as complete data and make bad operational calls ([Setproduct 2026 guide](https://www.setproduct.com/blog/data-table-ui-design)) |
| Shift-click as the *only* multi-column sort affordance | Undiscoverable — most users have never learned this exists in a web UI ([Adrian Roselli's sort experiment](http://adrianroselli.com/2021/06/multi-column-sortable-table-experiment.html)) |

## Open Questions

1. **Sticky header + sticky first column + row virtualization, all three at once** — this is documented as genuinely unresolved in the TanStack ecosystem as of the sources found (absolute-row-layout vs table-layout trade-off, see §1). You will need to prototype this early and decide whether to accept one of the documented compromises, switch to react-virtuoso (which claims sticky support out-of-the-box, unverified against your exact combination in this research pass), or build a custom scroll-sync solution.
2. **Per-table accessibility posture**: given AG Grid's own recommendation to disable virtualization for full a11y compliance, which of your 7 tables actually need full non-virtualized accessibility (likely: audit log, RBAC matrix — compliance-adjacent) vs. which can accept the `aria-rowcount`/`aria-rowindex` virtualized-with-caveats approach (likely: loads/trips/fleet/driver boards — operational speed matters more there)? This needs a decision, not a default. `[inferred prioritization — confirm with actual compliance/accessibility requirements for the carrier]`
3. **Row height variance from progress bars and multi-line chips**: how much does your actual cell content vary in height? If it's genuinely fixed-height (single-line chips, fixed-width progress bars), TanStack Virtual's fixed-size mode is much simpler and faster than dynamic `measureElement` sizing — worth constraining your design system's cell components to fixed heights per density mode rather than allowing organic variable height, purely for virtualization simplicity. `[inferred — not addressed directly in sources, extrapolated from AG Grid's noted buffer-shrinkage-under-variable-height issue]`
4. **RBAC matrix at mobile width** — no source directly addresses a 43-row × many-column permission matrix specifically; the role-picker fallback proposed above is reasoned from first principles, not evidenced. Worth a targeted look at how Okta, Auth0, or similar IAM consoles handle this if you want a directly-comparable reference (not covered in this research pass).
5. **Exact library choice (TanStack Virtual vs react-virtuoso)** should probably be settled by a half-day spike building the sticky-header + sticky-column + variable-row-height combination in both, since the sources disagree on how painful this is in each — the research surfaced the trade-off but not a definitive verdict for your exact combination of requirements.
