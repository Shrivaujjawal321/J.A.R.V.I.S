# Keyboard-First Design for an Expert-Use Dispatch Console

*Research brief — 2026-08-07. Research only; no code, no product decisions made here.*

## Quick answer

Speed for an expert user is not "add shortcuts" — it is a **layered system**: (1) a single global command palette (Cmd/Ctrl+K) that reaches anything in the app in two keystrokes, ranked by fuzzy-match score + recency/frequency, scoped to the current context; (2) a small set of **bare single-letter mnemonic shortcuts** for the handful of actions a user repeats hundreds of times a day, active only while the relevant list/grid has DOM focus (which also flips assistive tech into forms/focus mode, sidestepping most screen-reader collisions); (3) **arrow-key/roving-tabindex grid navigation** per the WAI-ARIA grid pattern as the accessible baseline, with `j`/`k` as an optional power-user overlay; and (4) **disciplined focus management** — focus never gets lost on drawer close, row delete, bulk action, or async completion, and every focus-trap has a documented exit. The published research consensus (Superhuman, Linear, Raycast, kbar/cmdk authors, NN/g, WAI-ARIA APG) agrees on the shape of this system; where it disagrees is only in the aggressiveness of shortcut coverage vs. the correctness of accessibility mode-switching, and that tension is real and needs to be tested with an actual screen reader, not just designed on paper.

## Proposed shortcut map for your product

Ground rules used to derive this:
- **Bare single letters are reserved for the handful of actions repeated hundreds of times a day** — per NN/g, accelerators should target high-frequency actions only ([nngroup.com/articles/ui-accelerators](https://www.nngroup.com/articles/ui-accelerators/)). Rarer actions get a secondary path (action menu / palette), not a scarce letter.
- **Global shortcuts** (work anywhere) use modifiers or chords to avoid firing while a user types in a field. **Row/grid-scoped shortcuts** are bare letters but are gated on the row/grid actually holding DOM focus — this is also what causes NVDA/JAWS to switch out of "browse mode" into "forms/focus mode," which is the mechanism that prevents most single-letter collisions with screen-reader quick-nav keys ([Deque University Screen Reader Survival Guide](https://dequeuniversity.com/screenreaders/survival-guide)).
- Collisions checked against the common NVDA/JAWS browse-mode quick-nav letters: **H, 1–6, T, L, I, G, F, R, Q, U, V, K, D** (heading, table, list, list-item, graphic, form, region/landmark, main-landmark, unvisited/visited link, next-link, region). Any bare letter chosen from this set is flagged below.

| Action | Shortcut | Why this key | Collision flag |
|---|---|---|---|
| Open command palette (search + run any action, anywhere) | **Cmd/Ctrl+K** | Industry-converged convention — Linear, Superhuman, Raycast, Vercel, GitHub, Height, VS Code all use it; users arrive already knowing it | Chrome/Edge natively bind Ctrl+K to "search via omnibox." Must `preventDefault()`; this works reliably once the page has focus (all cited products ship this exact override) — [command.ai discussion in Retool's writeup](https://retool.com/blog/designing-the-command-palette), [Superhuman](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/) |
| Local/page search or filter (lighter than full palette) | **/** | GitHub, Algolia docs, Notion convention: "/" focuses in-context search/insert, distinct from the global palette | Firefox's built-in "quick find" also binds `/`. Guard: only handle when no input/textarea is focused, and `preventDefault` |
| Show shortcut cheat-sheet overlay | **?** (Shift+/) | Universal convention (Gmail, Linear, Superhuman, Slack, GitHub) — progressive disclosure without a manual | None found |
| Jump to a section (Tenders, Board, Drivers, Assets, Reports) | **g** then **t / b / d / a / r** | Gmail's "go-to" prefix pattern; sequence (not chord) shortcuts are learned faster than arbitrary combos because the prefix is a consistent, meaningful signal — [Mailbird/Gmail shortcut docs](https://www.getmailbird.com/gmail-keyboard-shortcuts-2026-the-complete-hotkeys-list-for-power-users/) | Low risk — bare `g` does nothing alone, so it can't misfire; requires a short timeout window (Gmail-style, typically ~1–2s) between the two keys |
| Move focus between tender rows | **↓/↑ (baseline)**, **j/k (overlay)** | Arrow keys are the WAI-ARIA grid spec's required baseline ([W3C APG Grid Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)); `j/k` is the Vim/Gmail/Superhuman/Linear power-user layer on top, never a replacement | None — `j/k` only active while the grid has DOM focus |
| Open the focused tender (detail view / start of assign flow) | **Enter** | Matches the ARIA grid spec's own semantics for "activate/enter" and matches user mental model from every list-based tool researched | None |
| **Accept tender** | **A** | Mnemonic, first letter, not in the browse-mode quick-nav set — clean | None |
| **Assign truck + trailer** (opens 4-step wizard) | **Enter** (from row) as primary path; **T** as a direct-jump secondary | "Assign" collides with "Accept" (both start with A) inside one scheme, so this uses an object-based mnemonic (Truck) instead of a verb-based one, matching how Linear resolves verb clashes by keying off the object/resulting state rather than the verb | **Real collision**: `T` = "next table" in NVDA/JAWS browse mode. Mitigated by forms/focus-mode switch when the row has focus, but **flag for screen-reader testing before shipping** — this is the one place in the map where speed and accessibility genuinely compete |
| **Confirm POD** | **P** | Mnemonic ("Pod"), not in the quick-nav set | Low risk — some screen readers use `p` for "next paragraph" only in document-reading contexts (not app widgets); `[inferred]`, verify empirically |
| **Message driver** | **M** | Mnemonic, not in the quick-nav set | None |
| **Acknowledge detention** | *No bare letter — behind a row "quick actions" popover*, e.g. **.** to open, then type-ahead | Per NN/g, accelerators should target only the highest-frequency actions; detention ack is event-triggered and comparatively rare relative to accept/assign/message. Burning a scarce, hard-to-remember letter on a low-frequency action is the wrong trade. This mirrors Superhuman's nested-picker pattern (open a mini list, then type to filter) rather than a 6th raw mnemonic letter | `.` as an "open actions" key echoes GitHub's code-nav conventions; verify it doesn't collide with any in-app numeric/decimal input fields |
| Select row(s) for bulk action | **x** or **Space** | Gmail's `x`-to-select convention; Space is the ARIA-standard "toggle selection" key in listbox/grid patterns | None significant |
| Close drawer / cancel wizard / exit edit mode | **Esc** | Universal; also the WAI-ARIA-mandated exit from grid cell-edit mode | None — but see Focus Management section: Esc must also **return focus** to the element that opened the thing being closed |
| Submit the assign wizard from any step (power-user skip-ahead) | **Cmd/Ctrl+Enter** | Matches Linear/GitHub's "submit form" convention, avoids colliding with plain Enter's per-step "advance" behavior | None |

**Not shortcut-mapped, intentionally:** anything destructive (delete, unassign after confirmation, force-cancel a tender) gets **no bare-key shortcut** at all — per your Tier-3 confirm rule, these route through a confirm dialog regardless of input method, and putting them behind a fast key invites exactly the kind of muscle-memory misfire NN/g and WCAG's "no keyboard trap" guidance both warn about.

## Evidence per topic

### 1. Command palette

- **What belongs in it, how it's ranked**: cmdk's author and production users (Vercel command menu) treat the palette as a single surface for search *and* action execution, filtered/sorted automatically as you type, with an overridable `filter` function and keyword aliases feeding the ranking — [cmdk (pacocoursey)](https://github.com/pacocoursey/cmdk).
- **Retool's concrete lesson**: don't split "search" and "actions" into separate modes (their explicit critique of VS Code's model) — combine them on one surface, because users don't want to decide upfront whether they're searching or doing. They also solved a real ranking bug: grouping results into sections (by type) can bury the single best match, so they added a "Top result" section that always shows the strongest match regardless of category — [Retool: Designing the Command Palette](https://retool.com/blog/designing-the-command-palette).
- **Context sensitivity**: Cmd+K does mean something different depending on where you are, by design. Retool built a scoping/breadcrumb model — deleting a "context pill" moves you up in scope, selecting a result moves you down. In kbar, actions are registered/torn down with `useRegisterActions` inside the component that owns the relevant screen, so an action only exists while its screen is mounted; in cmdk you conditionally render `Command.Item`s by route — [kbar](https://github.com/timc1/kbar), [Retool](https://retool.com/blog/designing-the-command-palette). Notion goes further and gives a *different* palette by trigger key: `/` for the general create/edit palette, Space for an AI-only palette — a second real example of "the same shortcut region meaning something different depending on context."
- **Superhuman's design rules** (from their own build-it writeup): the palette must be reachable everywhere via one consistent, memorable shortcut that doesn't clash with typing; all commands live in one centralized place ("omnipotence" — every action reachable); matching must be forgiving (case-insensitive, typo-tolerant, synonym/alias-aware); ranking blends a baseline relevance score with contextual boosts (e.g., boost "reply" when a conversation is focused) — [Superhuman: How to build a remarkable command palette](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/).
- **Where the pattern fails**: Sublime Text's fragmented multiple "Go To" palettes ("remembering which set of hotkeys corresponds to which command just doesn't work" — a single entry point with query-prefixes like `@` for symbols is the better model); Raycast's early limitation to exact substring matching (vs. true fuzzy) as a counter-example of what *not* to do — [Destiner: Designing a Command Palette](https://destiner.io/blog/post/designing-a-command-palette/). Retool separately flags the anti-pattern of surfacing every result unscoped/uncategorized, and of forcing a modal switch between "search mode" and "action mode."
- **Raycast's framing** (useful for your product's philosophy, not just the palette widget): "search as the first step in doing, not the last step in finding" — the palette should let you find *and* act in the same gesture, not find-then-navigate-then-act — [Raycast coverage, XDA](https://www.xda-developers.com/raycast-showed-me-what-command-palette-can-become/), [pixelmatters](https://www.pixelmatters.com/insights/raycast-for-software-engineers).
- **GitHub's implementation** is a useful "modes within one palette" reference: typing narrows to a mode (repos, files, issues, PRs), arrow keys highlight, Enter navigates, Tab narrows scope by adding a highlighted repo/org as a filter — [GitHub Docs: Command Palette](https://docs.github.com/en/enterprise-cloud@latest/get-started/accessibility/github-command-palette).

### 2. Shortcut system design

- **Sequence (chorded prefix) vs. simultaneous modifier**: Gmail's `g` + a second key ("go to") is a *sequence* — press, release, press — not a chord. It's a prefix namespace: `g i` = inbox, `g s` = starred, `g d` = drafts, `g a` = all mail, `g c` = contacts, `g k` = tasks — [Gmail shortcuts documentation, e.g. getmailbird.com summary](https://www.getmailbird.com/gmail-keyboard-shortcuts-2026-the-complete-hotkeys-list-for-power-users/). Superhuman layers Vim-style `j/k` (up/down between messages) and `h/l` (between panes) on top of this, plus its own Cmd+K command surface — [Superhuman Help Center: Speed Up With Shortcuts](https://help.superhuman.com/hc/en-us/articles/45191759067411-Speed-Up-With-Shortcuts).
- **Avoiding browser/OS/screen-reader collisions**: Conflicts surface at three layers that overlap in the same single-character keyspace — browser (Alt+letter menu access, Ctrl+letter), OS (Cmd+S, Ctrl+W), and screen reader (JAWS Alt+letter, NVDA Insert+letter, VoiceOver Ctrl+Option+letter), and *bare* single letters additionally collide with screen-reader browse-mode quick-nav keys (see topic 7). The MDN guidance on `aria-keyshortcuts` states plainly that overriding a screen reader's own shortcuts "completely shuts down access" for that user, and recommends avoiding bare single letters in favor of at least one modifier for anything global — though products like Gmail/Linear/Superhuman do use bare letters successfully because they scope them to a focused, mode-switching widget rather than firing globally — [MDN: aria-keyshortcuts](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-keyshortcuts).
- **Discoverability without a manual**: NN/g's guidance is to make accelerators "readily available, yet easy to ignore" — reveal them progressively (after a user performs an action the standard way, once, show the shortcut as a hint), and to concentrate design effort on features people already use repeatedly rather than exposing every possible shortcut up front — [NN/g: Accelerators Maximize Efficiency in User Interfaces](https://www.nngroup.com/articles/ui-accelerators/). Knock's design guide operationalizes this into three traits every shortcut needs — discoverable (tooltip/reference/palette), memorable (mnemonic, spatial mapping — left keys for left UI, top keys for top UI), and conflict-free — and recommends a `?`-overlay plus a centralized reference as the standard discovery mechanism — [Knock: How to design great keyboard shortcuts](https://knock.app/blog/how-to-design-great-keyboard-shortcuts).
- **How many shortcuts people actually learn**: No source found gives a hard universal number; the honest answer is "it depends on repetition frequency, not a fixed ceiling." What is reasonably well evidenced: most users never discover shortcuts that aren't surfaced somewhere in the UI (the oft-cited example is that a large share of users don't know Cmd/Ctrl+F exists despite it being decades old) — a discovery search surfaced this figure only in a snippet from a since-redirected page and it should be treated as `[unverified — could not confirm on a live source]`, not a hard citation. What's solidly sourced is the *design implication*: rely mostly on one- or two-letter shortcuts to minimize memory burden, and reserve them for the small set of actions a specific user actually repeats — [NN/g](https://www.nngroup.com/articles/ui-accelerators/), [Knock](https://knock.app/blog/how-to-design-great-keyboard-shortcuts).

### 3. Focus management

- **The core failure mode**: when a modal/drawer closes, focus should return to the element that opened it, not fall back to `<body>` — this is a WCAG 2.4.3 (Focus Order) violation when missed, and it's flagged as one of the most common accessibility bugs in production ("the mistake 90% of devs make," per one widely-cited writeup). Browser inconsistency makes it worse: in Safari, `document.activeElement` can incorrectly report `<body>` after a click rather than the actual trigger element, which breaks naive "save and restore focus" implementations — [Deque: When the modal is closed, focus is not returned to the triggering element](https://docs.deque.com/issue-help/1.0.0/en/focus-modal-not-returned/), [react-modal issue #279](https://github.com/reactjs/react-modal/issues/279), [bootstrap issue #12364](https://github.com/twbs/bootstrap/issues/12364).
- **Focus trapping done correctly**: keyboard focus must stay inside an open modal (Tab/Shift+Tab cycle within it, never escaping to background content), but there must always be a documented way out (Escape, or an explicit close control) — this is exactly what WCAG 2.1.2 "No Keyboard Trap" requires: "if focus can be moved to a component using the keyboard, focus can also be moved away using only the keyboard... if it requires more than unmodified arrow/tab keys, the user must be advised how" — [W3C: Understanding SC 2.1.2 No Keyboard Trap](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html).
- **After a row is deleted / after bulk action**: not directly covered by a single canonical source in this research pass, but the pattern implied by the WAI-ARIA grid spec's roving-tabindex model and general focus-restoration guidance is: focus should move to the next logical row at the same position (or the new item occupying that position), never vanish to `<body>`. `[inferred]` — flagged as a design decision to explicitly test, since it's the exact bug class ("focus falls off a cliff after delete") that shows up repeatedly in the modal-focus bug reports above, just for list mutation instead of modal close.
- **After an async action completes**: no canonical published guidance found specific to this case in this pass; the safe default consistent with the above sources is to keep focus stationary on the triggering control/row and communicate completion via a non-focus-stealing signal (toast/inline status), only moving focus if the action removed the focused element from the DOM. `[inferred]`.
- **Roving tabindex**: exactly one element in a group has `tabindex="0"` (reachable by Tab), all siblings have `tabindex="-1"`; arrow keys move focus and shift which element has `tabindex="0"`; the group behaves as a single Tab stop, which is both the accessibility-correct approach and the fast-navigation approach (they're the same mechanism, not competing ones) — [MDN/eBay MIND Patterns: Roving Tabindex](https://ebay.gitbook.io/mindpatterns/techniques/roving-tabindex), [jakelazaroff: roving-tabindex](https://jakelazaroff.github.io/roving-tabindex/).

### 4. Navigating a data grid by keyboard

- **WAI-ARIA grid pattern, keyboard table** ([W3C APG: Grid Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)):
  - Arrow keys move focus one cell in that direction.
  - `Home`/`End` move to first/last cell **in the current row**; `Ctrl+Home`/`Ctrl+End` move to the first/last cell **in the whole grid**.
  - `Page Up`/`Page Down` move focus by an author-defined number of rows.
  - `Enter` or `F2` disables grid navigation and moves focus into the cell's editable widget; `F2` toggles back out, `Escape` always restores grid navigation.
  - Only one focusable element in the whole grid sits in the page's Tab sequence (roving tabindex) — Tab/Shift+Tab move *out of* the grid entirely, not between cells.
- **`j`/`k` as an overlay, not a replacement**: Superhuman and Linear both add Vim-style `j/k` row navigation on top of (not instead of) arrow-key support, because `j/k` is a power-user accelerant while arrow keys remain the accessible, discoverable, spec-compliant baseline — [Superhuman Help Center](https://help.superhuman.com/hc/en-us/articles/45191759067411-Speed-Up-With-Shortcuts).
- **Where real products deviate from the spec and why**: most production grids (Linear's issue list, Superhuman's message list) are not full ARIA `grid`s at all — they're `listbox`/`list` patterns with single-column row selection, because a true 2D `grid` role is heavier to implement correctly and most dispatch-style UIs only need row-level (not cell-level) keyboard interaction. Reserve the full grid pattern (with cell-level Enter/F2 edit mode) for genuinely spreadsheet-like editing surfaces; for a row-of-actions list like a tender queue, the simpler `listbox`-with-roving-tabindex model is the better match to both the spec's intent and to what Linear/Gmail/Superhuman actually ship. `[inferred from cross-referencing the spec's own grid-vs-listbox distinction with observed shipped products; not a single direct citation]`.

### 5. Multi-step flows by keyboard

- WAI's general guidance for multi-step/multi-page forms (via the "Multi-page Forms" pattern referenced in current accessibility coverage) calls for: a visible step indicator, logical Tab order matching the reading/visual order, and state that survives navigating back a step (no data loss on Shift+Tab-equivalent "back") — [UXPin: Keyboard Navigation Patterns for Complex Widgets](https://www.uxpin.com/studio/blog/keyboard-navigation-patterns-complex-widgets/), [uxpatterns.dev: Wizard/Stepper Pattern](https://uxpatterns.dev/patterns/advanced/wizard).
- Concretely, for a keyboard-only expert to complete a 4-step wizard without the mouse, the pattern that emerges from combining the grid/listbox spec with common product convention is: `Enter` submits the current step and advances; `Shift+Tab` out of the first field of a step (or a dedicated "Back" affordance) returns to the previous step without losing entered data; within any step that asks the user to choose from a list of assets (your truck/trailer picker), that picker should be a `combobox`+`listbox` (ARIA combobox pattern) with type-ahead filtering and arrow-key selection, not a native `<select>`, so the same fuzzy-typing muscle memory as the command palette applies; a "skip to end and submit" power-user shortcut (`Cmd/Ctrl+Enter`) matches the convention GitHub and Linear use for form/PR submission from anywhere in a multi-field form. `[inferred — synthesized from the wizard-pattern and grid/combobox specs above; no single source describes a 4-step asset-assignment wizard directly]`.

### 6. Type-ahead and fuzzy matching

- **fzf's algorithm** (the reference implementation most JS libraries emulate): parses the query, matches each candidate as an ordered subsequence (not requiring contiguous characters), and scores matches to rank them — the default "v2" algorithm is tuned to guarantee the best-scoring match is found, not just *a* match — [fzf (junegunn)](https://github.com/junegunn/fzf), [DeepWiki: fzf fuzzy matching algorithm](https://deepwiki.com/junegunn/fzf/2.2-fuzzy-matching-algorithm). A JS port (`fzf` on npm, `fzf-for-js`) exists for exactly this "bring fzf's scoring into a web command palette" use case.
- **What makes ranking "feel right"** (synthesized across Superhuman, Retool, cmdk): pure textual match score is not sufficient — production palettes blend (a) subsequence/fuzzy match quality, (b) a contextual boost/dampen multiplier per action (e.g., boost "reply" when a message is open), and (c) usage signal (recency/frequency of that user invoking that action) — [Superhuman](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/), [Retool](https://retool.com/blog/designing-the-command-palette). cmdk itself is deliberately unopinionated here — it ships a default filter/sort but exposes a `filter` prop so you can swap in fzf-style scoring or your own ranking function — [cmdk](https://github.com/pacocoursey/cmdk).

### 7. Accessibility, honestly

- **Where power-user and screen-reader design agree**: roving tabindex is literally the same mechanism used for both fast keyboard navigation and correct screen-reader navigation — there is no accessible-vs-fast tradeoff here, only one correct implementation ([eBay MIND Patterns](https://ebay.gitbook.io/mindpatterns/techniques/roving-tabindex)). Likewise, `aria-keyshortcuts` lets you expose your app's shortcuts *to* assistive tech rather than hiding them, turning a potential conflict into a discoverability win if implemented ([MDN](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-keyshortcuts)).
- **Where they genuinely conflict**: bare single-letter app shortcuts (Gmail's `e` for archive, your proposed `A`/`P`/`M`) only work safely because focus is inside a widget that has switched the screen reader out of "browse mode" into "forms/focus mode." NVDA/JAWS browse-mode quick-nav uses nearly the full alphabet for content navigation (H=headings, T=table, L=list, I=list-item, G=graphic, F=form, R/Q=landmarks, U/V/K=links, D=region) — [Deque University Screen Reader Survival Guide](https://dequeuniversity.com/screenreaders/survival-guide). Any bare-letter shortcut that fires *outside* a properly-focused, correctly-ARIA-labeled widget will silently break for screen-reader users in browse mode. This is exactly why the shortcut map above gates every bare letter on the grid/row actually holding DOM focus, and flags `T` specifically as needing real screen-reader testing.
- **WCAG 2.2 requirements that bear directly on this project**:
  - **2.1.2 No Keyboard Trap (A)** — any modal/drawer must be exitable via keyboard alone ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html)).
  - **2.4.11 Focus Not Obscured (Minimum) (AA)** — a focused element must not be entirely hidden by other content (e.g., a sticky header covering a focused row) — [Vispero: New Success Criteria in WCAG 2.2](https://vispero.com/resources/new-success-criteria-in-wcag22/), [Deque: WCAG 2.2 Proposed Recommendation](https://www.deque.com/blog/wcag-2-2-is-at-the-proposed-recommendation-stage/).
  - **2.5.8 Target Size (Minimum) (AA)** — interactive pointer targets must be at least 24×24 CSS px (with a spacing exception) — relevant to your row action buttons and any icon-only controls — [Vispero](https://vispero.com/resources/new-success-criteria-in-wcag22/).
  - **2.4.7 Focus Visible** (existing, carried into 2.2) plus the new AAA-level **2.4.13 Focus Appearance** raises the bar to a ≥2px perimeter indicator with ≥3:1 contrast — worth targeting even though it's AAA, given how much time this user spends keyboard-navigating — [Vispero](https://vispero.com/resources/new-success-criteria-in-wcag22/).

## Anti-patterns and the failure each causes

1. **Firing bare single-letter shortcuts at `document` level regardless of focus.** Causes: screen-reader browse-mode collisions (topic 7), and shortcuts misfiring while a user is typing in an unrelated text field. Fix implied by all cited sources: scope to a widget's DOM focus state.
2. **Splitting search and actions into separate modes/palettes** (Retool's explicit critique of the VS Code model; Destiner's critique of Sublime's fragmented "Go To" palettes). Causes users to have to decide *before* they've typed anything whether they're "searching" or "doing," adding a decision cost the palette was supposed to eliminate.
3. **Not returning focus after a modal/drawer closes.** Causes WCAG 2.4.3 violations and a disorienting "where am I" experience for keyboard users — the single most commonly cited focus bug across the sources reviewed ([Deque](https://docs.deque.com/issue-help/1.0.0/en/focus-modal-not-returned/), multiple framework GitHub issues).
4. **Overriding a shortcut a screen reader or browser already owns, without checking.** Causes total loss of access for AT users on that key, per MDN's explicit warning ([MDN aria-keyshortcuts](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-keyshortcuts)).
5. **Using a full ARIA `grid` role/interaction model for a simple row-of-actions list.** Causes unnecessary implementation complexity and a worse experience than the simpler `listbox`+roving-tabindex pattern that Linear/Gmail/Superhuman actually use for exactly your use case (a tender queue is a list of rows with actions, not a spreadsheet). `[inferred]`.
6. **Teaching shortcuts only via a help-menu manual nobody reads.** Contradicts NN/g's progressive-disclosure guidance directly — the fix is inline hints (show the shortcut next to the action after the user does it the slow way once) plus a `?`-triggered overlay, not documentation alone ([NN/g](https://www.nngroup.com/articles/ui-accelerators/), [Knock](https://knock.app/blog/how-to-design-great-keyboard-shortcuts)).
7. **Burning scarce single-letter mnemonics on low-frequency actions.** Directly contradicts NN/g's "accelerate what's used repeatedly" guidance and creates memory burden with poor payoff — this is why "acknowledge detention" is *not* given a bare letter in the map above.
8. **Disabling the focus indicator or shrinking it below the WCAG 2.2 focus-appearance bar** because it "looks cleaner." Causes exactly the kind of "I don't know where I am" failure that defeats the entire point of a keyboard-first console for a user who lives in it all day.
